# 飞书 × Amazon Quick 集成方案怎么选

> cast: 主讲=news-male-formal, 提问=narrator-female-warm
> format: long

## 四个方案，两类需求

提问（设问）：飞书和 Amazon Quick 要集成，一搜好几种做法，到底该选哪一个？

主讲：先别看方案，先看需求。客户的需求其实只有两类：一类是让 Quick 去操作飞书，比如查文档、发消息、走审批；另一类是用飞书账号登录 Quick。

主讲：第一类叫 MCP 功能对接，有三个方案。第二类是身份认证，只有一个方案，就是飞书 SSO 单点登录。四个方案，两条主线，先把这个分岔记住，后面就不会乱。

![素材](il:decision,choice)

- 操作飞书 → MCP
- 登录 Quick → SSO
- 三 + 一 四方案

## 共同前提

主讲：不管走哪条路，有两件事绕不过去：飞书开放平台的相关权限，和用户的 OAuth 授权。这是四个方案的共同地基。

主讲（严肃）：但有一个差异必须注意。方案一、方案三、方案四，都需要在飞书开放平台创建自建应用，拿到 App ID 和 App Secret，而且要经过管理员审批发布才能用。

主讲：只有方案二不用。它在飞书的 MCP 配置平台上直接操作，不需要单独创建自建应用。这也是它上线最快的根本原因。

![素材](il:checklist,requirements)

- 开放平台权限
- 用户 OAuth 授权
- 一三四建应用
- 方案二免建

## 决策路径一张图

提问：那这四条路，怎么走到自己该选的那一个？

主讲：从客户需求出发，往上是「让 Quick 操作飞书」，分出方案一、二、三；往下是「用飞书账号登录 Quick」，对应方案四。

主讲：注意方案四是独立可叠加的。它跟前面三个不冲突，一个企业完全可以既做 MCP 对接，又做 SSO 登录。

![决策路径](assets/lark-quick/01-decision-path.png)

- 上分支是 MCP
- 下分支是 SSO
- 方案四可叠加

## 方案一：lark-cli 本地 MCP

主讲：第一个方案，在本地装一个 lark-cli，用 Stdio 方式挂成 MCP 服务。

主讲：好处是 lark-cli 的全量 API 都能用，部署也轻，装个命令行就行。代价是它只能在 Desktop 客户端用，而且是单用户——一台机器，一个人的凭证。

主讲（严肃）：所以它的定位很清楚：PoC 和技术验证。想先跑通看看效果，用这个最快。但别拿它支撑生产。

![素材](il:coding,laptop)

- 全量 API
- 仅 Desktop
- 单用户
- 定位 PoC

## 方案二：Remote MCP 直连

主讲：第二个方案，直接连飞书官方的 Remote MCP。零代码，页面上配一下就行，部署难度是四个里面最低的。

主讲：它支持 Web 和 Desktop 两个客户端，多用户天然支持，运维也完全不用管，因为是飞书托管。

主讲（严肃）：但它有一条硬边界：只能用飞书预设的工具包，覆盖度有限，而且不可自定义。你缺的能力它没有，你也加不上去。

![素材](il:network,connection)

- 零代码配置
- Web + Desktop
- 天然多用户
- 工具包有限

## 方案三：AgentCore 自建 MCP

主讲：第三个方案，用 AgentCore 自己建一个 MCP 服务。它的底层还是 lark-cli，所以 API 是全量的。

主讲：部署用 CDK 一键完成，支持 Web 和 Desktop，支持多用户，可扩展性好，而且是全托管服务，运维成本很低。

主讲：它的定位是企业级生产部署。要长期在生产环境里跑，这是最稳的一条路。

![素材](il:data,center)

- 全量 API
- CDK 一键部署
- 多用户可扩展
- 企业级生产

## 什么时候从方案二升到方案三

提问（设问）：既然方案二零代码就能用，为什么还要折腾方案三？

主讲：看三个信号。第一，飞书 MCP 的预设工具包不覆盖你要的功能，比如审批、人事，或者你自己的自定义 API。

主讲：第二，你需要定制扩展，比如加一层鉴权、加审计日志、加限流。第三，你需要集中管控多个用户的身份。

主讲（严肃）：这三条出现任意一条，就该往方案三迁了。反过来说，都没出现，就别提前上复杂度。

![素材](il:settings,configuration)

- 工具包不覆盖
- 要鉴权审计
- 要限流
- 多用户管控

## 横向对比：部署与覆盖

主讲：把三个 MCP 方案放到一起横向比。先看部署难度：方案二最低，零代码页面配置；方案一要在本地装 CLI；方案三是 CDK 一键部署。

主讲：再看支持的客户端：方案一只有 Desktop；方案二和方案三都是 Web 加 Desktop，覆盖更全。

主讲：最后看 API 覆盖度：方案一和方案三都是 lark-cli 全量 API；方案二是飞书预设工具包，有限。

![素材](il:report,analysis)

- 部署二最省事
- 客户端二三全
- 覆盖一三全量

## 横向对比：多用户与运维

主讲：多用户方面：方案一不支持，只能单用户；方案二天然支持；方案三也支持。

主讲：可扩展性：方案一和方案三都灵活，方案二不可自定义。运维：方案一在本地，没有运维；方案二飞书托管，也没有；方案三是全托管服务，运维很低。

主讲：所以定位就自然浮出来了：方案一做 PoC 技术验证，方案二做企业快速接入，方案三做企业级生产部署。

![素材](il:team,work)

- 多用户一不行
- 扩展一三灵活
- 运维都很轻
- 定位各不同

## 方案四：飞书 SSO 单点登录

主讲：最后是方案四，飞书 SSO 单点登录。它解决的是另一件事：让用户用飞书账号直接登录 Quick。

主讲：实现上是 Cognito 加 Serverless 做一层桥接。适用场景很明确：企业没有现成的 IdP 的时候，用它。

主讲：它跟前面三个方案相互独立，可以叠加。你完全可以一边用飞书账号登录，一边用 MCP 操作飞书。

![素材](il:authentication,security)

- 飞书账号登录
- Cognito 桥接
- 无 IdP 时用
- 可与 MCP 叠加

## 怎么选：三句话

主讲：总结成三句话。只是想验证技术可行性，选方案一，本地装 lark-cli，最快看到效果。

主讲：企业要快速上线，而且需求在飞书预设工具包的范围内，选方案二，零代码。

主讲：要进生产、要全量 API、要定制扩展和多用户管控，选方案三 AgentCore。需要飞书账号登录的，再叠加方案四 SSO。

![素材](il:target,goal)

- 验证选方案一
- 快上线选二
- 进生产选三
- 要登录加四

## 最后一句提醒

主讲（严肃）：最后提醒一句：方案二和方案三之间是可以平滑演进的。先用方案二快速验证业务价值，等边界不够了，再迁到方案三。

主讲：但方案一是验证用的，别直接拿去支撑生产。四个方案的实施细节，都在文档里对应的 Blog 和 GitHub 链接里。

![素材](il:rocket,launch)

- 二到三可演进
- 一别上生产
- 细节看文档
